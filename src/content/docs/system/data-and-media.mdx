D1 is the system of record. R2 holds the bytes that do not belong in relational rows. The Email Worker uses KV for a narrow receipt-intake job where short-lived leases and retry records matter more than relational queries.

The API Worker owns the operational D1 and R2 paths. The Email Worker owns its `RECEIPT_DEDUPE` KV namespace. The website, Discord Worker, and scheduler do not receive direct D1 or R2 bindings.

These records give every surface the same answer. A gallery page and a Discord notification can refer to one photo row. A dashboard loan and an equipment reminder can refer to one loan state. The schedule timer and a staff action can use the same studio request transition.

The API uses parameterized D1 queries and typed access helpers. Some domains use Drizzle; others use focused database modules where direct D1 statements better match the existing route. The important boundary is consistent: request handlers do not pass a database binding to the browser or to another service.

## The gallery and competition upload boundary

An upload is rejected before R2 receives it if the caller or file is outside the contract.

The exact limits vary by domain. Gallery and competition submissions use this paired-image path:

1. Resolve the session and require the correct membership or staff permission.
2. Apply the upload-specific rate limiter.
3. Parse a bounded multipart request.
4. Check the declared media type and the actual accepted image contract.
5. Enforce the byte limit and image dimensions.
6. Receive the full image and caller-prepared thumbnail.
7. Write both accepted objects to R2.
8. Write the D1 row that connects the public record to those objects.

The hard limits belong at more than one layer. A browser file picker can explain the limit early, but the API still checks the bytes because a caller can bypass the UI.

### Why these routes write R2 before D1

The API needs final object keys before it can commit the row that refers to them. That creates a short window where R2 contains new objects but D1 does not yet contain the corresponding record.

The gallery and competition compensation paths close that window. If the database insert fails, those handlers delete the new full-size and thumbnail objects before returning an error. The failed upload does not become visible and the submitted pair is not left unreferenced.

This is not a distributed database transaction; R2 and D1 do not share one commit. It is an explicit two-step write with cleanup for the second-step failure.

That cleanup is not universal across every media route. Avatars, event images, leadership images, and merchandise use their own single-object flows. Leadership creation currently writes its R2 object before D1 without an equivalent insert-failure cleanup, so that route needs separate attention when its write path changes.

## Public image reads

Gallery and competition image routes receive an opaque photo or entry ID. The API looks up that ID in D1, obtains the stored object relationship, checks the route's visibility rules, and then streams the R2 body. Profile avatar reads follow the same record-first idea with their own route shape.

That indirection gives the API room to:

- Return `404` for a missing or no-longer-visible record.
- Change an internal object key without rewriting every public link.
- Apply cache and content headers in one place.
- Keep bucket layout out of the browser contract.
- Delete a database record and its media through one domain workflow.

This indirection is a common pattern, not a platform-wide guarantee. Merchandise currently serves `/api/merch/image/:imageR2Key`, so its public URL exposes the stored key directly. Any change to key layout must account for those links.

## KV: a narrow intake queue, not the database

The Email Worker binds one KV namespace named `RECEIPT_DEDUPE`. It stores receipt-intake dedupe state, processing leases, retry records, and terminal results for normalized payloads that reached the intake state machine.

Calling it a queue can be convenient in conversation, but it is not Cloudflare Queues. The repository does not configure a Queue binding. The worker writes retry records to KV and its own five-minute cron scans eligible work.

KV handles the submission problem after parsing: “Are we already processing or retrying this normalized purchase?” D1 handles the business problem: “Has this purchase already produced its membership key, email, or Discord side effect?” Both layers share the purchase's logical idempotency identity, but use different storage-key prefixes, records, lifetimes, and responsibilities.

The website also declares a `SESSION` KV binding. Better Auth sessions in the current API are stored in D1, and no direct source use of that website binding was found while this guide was prepared. It should be treated as configured infrastructure, not described as the active session database without confirming a later code change.

## What is not in the storage stack

There are no configured Cloudflare Queues or Durable Objects in this checkout.

That matters when reading the code:

- Receipt retries are KV records, not queue messages.
- Scheduled concurrency is a D1 lease, not a Durable Object lock.
- Discord replay protection is a D1 nonce claim, not an in-memory Worker set.
- The VPS Gateway owns the persistent Discord websocket because a normal request Worker does not stay alive as a permanent socket process.

Adding a Queue or Durable Object later could be a sensible architectural change for a specific problem, but this guide documents the system that exists in the repository now.

## Data consistency in club workflows

Operational domains keep state transitions in the API so side effects can follow a committed decision.

For an equipment loan, the API validates the borrower and item, writes the loan transition and audit information, then dispatches any required Discord update. For a film or studio request, the API owns review state and cancellation rules before Discord posts or DMs change. For a competition, the API coordinates entry rows, results, deletion claims, and R2 cleanup.

This ordering keeps a failed Discord request from becoming the only record that something happened. D1 remains the source that can be retried, inspected, or repaired.

## Privacy and exposure boundaries

The storage bindings exist only inside trusted Workers. Public routes return the fields and bytes needed for that page rather than exposing whole tables or bucket listings.

Private account, session, challenge, nonce, receipt, and audit records are not part of public response contracts. Error responses avoid returning SQL text, object keys, secrets, or stack traces. Logs carry operational context, but the shared logging helpers redact common credential fields before structured output.
