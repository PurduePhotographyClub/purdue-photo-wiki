The Scheduler Worker is intentionally boring. Every thirty minutes it builds six private API requests, sends them in parallel, records a summary, and stops.

It does not know how a membership expires. It does not know which equipment loan needs a reminder. It does not know how to edit a Discord post. Those decisions stay in the API and Discord Worker.

The scheduler source file keeps the paths in one fixed list. Adding a seventh job requires an explicit code change and deployment; a database row cannot make the Worker call an arbitrary internal URL.

## One trigger, six parallel requests

Cloudflare Cron invokes the Worker's `scheduled` handler with the cron string and scheduled timestamp. The Worker checks for its `INTERNAL_TOKEN` and `API_WORKER` binding, then maps the six paths into `Promise.all`.

Parallel dispatch matters because the jobs are independent. A darkroom stats calculation should not wait for a membership expiry scan, and an equipment reminder should not delay studio schedule work.

Each result records:

- The API path.
- Whether the HTTP response was successful.
- The status code.
- A bounded response body.
- The duration in milliseconds.
- A safe error message when the request threw before a response.

The final summary counts successful and failed jobs. One failure does not erase the results of the other five.

The source header is not trusted by itself. A browser can invent a header name. The internal token and service-binding path establish the trusted caller context.

The API routes these job paths before normal browser-session authorization. They are private service endpoints, not staff dashboard endpoints and not public cron URLs.

## D1 leases stop overlapping work

Cron systems can deliver again after delays or uncertainty. Deployments can also create a short overlap around a scheduled boundary. The API uses D1 scheduled-job state to claim a lease before a domain job runs.

A lease provides three useful facts:

1. Whether another invocation is already running the same named job.
2. When the current claim expires if a Worker dies before completion.
3. The completion or failure status operators can inspect later.

If a second invocation arrives while the lease is valid, it does not run the domain work again. When the owner finishes, it records success or failure and releases or advances the state according to the job helper.

## The API still owns idempotency inside a job

A job lease stops two copies of the same scheduled job from running at once. Domain code still needs careful write rules.

An equipment reminder, for example, should record or derive which reminder is due before it dispatches a Discord event. A membership expiry should transition only memberships that are actually elapsed. A photographer request sweep should update only requests in the expirable state.

The lease protects execution. Domain predicates protect individual records.

## Discord work stays on the Discord path

Several scheduled jobs produce Discord-visible changes. The scheduler does not call Discord REST and does not receive a Discord token.

The path remains:

1. Scheduler calls the private API job.
2. API claims the scheduled-job lease.
3. API finds and commits the required domain changes.
4. API signs typed Discord events for the changes that need Discord side effects.
5. Discord Worker verifies, claims each nonce, and dispatches the REST work.

This keeps scheduled and manually initiated changes on the same event contract.

## Health and rate limits

The Worker exposes a small health response with its service name and configured job count. Health calls have their own rate-limit check so the route cannot be used as an unbounded request sink.

The scheduler configuration also declares a ten-per-minute rate limiter, but the current code applies it only to public `GET /` and `GET /health` requests. The scheduled handler does not pass through that limiter. Cron execution relies on Cloudflare's scheduled trigger, and the resulting API calls rely on the private binding and internal token.

## Scheduler failures

Failures fall into two levels.

### Request-level failure

One API call can return a non-success status or throw before a response. The Worker captures that path's result and continues waiting for the other jobs. The summary logs the failed and successful counts.

### Domain-level failure

The API can acquire a lease and then fail inside a job. The scheduled-job state records failure, the API logs domain context, and the Scheduler Worker sees the non-success response.

Neither level is hidden by a blanket “cron ran” message. A trigger can run successfully while one of six jobs fails, so the summary keeps the paths separate.

## The five-minute email cron is different

The Email Worker also has a Cron trigger, but it is not part of this six-job scheduler.

Its five-minute schedule scans the receipt KV namespace for retryable intake records. That timing belongs to email parsing and delivery recovery, so it stays with the Email Worker. The thirty-minute Scheduler Worker is reserved for API-owned club workflows.
