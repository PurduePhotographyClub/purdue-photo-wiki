The short version: the website talks to one backend. That backend owns the rules and data. When something has to happen in Discord, the API hands it to the bot worker. The scheduler only keeps time, and the email worker only handles incoming receipts.

That split is intentional. A page does not update Discord directly. The scheduler does not edit the database. The email worker does not create memberships by itself. Each service has a narrow job, and the API is the point where those jobs become club data.

The wiki sits beside that operational chain. It is an independent Astro and Starlight project built into static HTML, indexed with Pagefind, and published to Cloudflare Pages. Reading this guide does not depend on the member API being available.

## One center of gravity

The API Worker is the system's center of gravity because it is the only place that sees the full combination of identity, permissions, club state, and storage. A request may start in the website, Discord, an email, or a timer, but the decision about what should change belongs to the API.

That gives the rest of the platform a simple rule:

<div className="my-8 border-l-2 border-amber-200 bg-amber-200/[0.04] p-6 sm:p-8">
  <p className="m-0 font-['Playfair_Display',Georgia,serif] text-2xl leading-snug text-white">If a change affects club data, membership, permissions, or a workflow state, it goes through the API.</p>
</div>

The rule prevents two services from inventing different answers. Discord and the dashboard see the same equipment loan. A receipt and an activation form use the same membership records. A scheduled expiry follows the same domain rules as a manual action.

The workspace is made from nested repositories rather than one deployable package.

Service bindings keep Worker-to-Worker traffic off the public internet. Shared secrets and signed event envelopes still matter because the receiving service must know who created a request and whether anyone changed it in transit.
